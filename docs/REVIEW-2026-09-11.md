> 审查对象：本地快照 `0.2.0-alpha03`（259 个文件 / 约 23,000 行 Kotlin / 10 个 Gradle 模块）
> 审查方式：静态阅读全部关键源码 + 离线运行 `:ptp :upnp :lut :core` 单元测试 + GitHub API 检索同类开源项目
> 日期：2026-09-11

> **进展更新（2026-09-11 同日）**：第 1 节全部 P0 缺陷与第 5 节 P0 清单**已全部落地**
> （含新增的 `WifiQrParserTest` 回归测试与 `THIRD_PARTY_NOTICES.md`），

## 0. 总体结论

**协议与可靠性内核的水准高于同类开源项目的平均线。** PTP/IP 事务互斥、超时自愈、
保活分级、句柄失效、通道切换与下载的互斥关系、静默期让路写卡——这些真机踩坑都被
写进了代码结构而不是只写在注释里，且有对应的防御性实现（非法 count 上限、内存路径
64MB 上限、socket 泄漏回收、半成品文件清理）。纯协议模块不依赖 Android、不依赖 DI，
分包合理，注释里保留"为什么"的决策记录，这在个人开源项目里是稀缺品。

短板不在内核，而在三处"外围"：

1. **对外一致性**：README / HANDOFF / CHANGELOG 与实际代码已经漂移（版本号、模块表、
   compileSdk、甚至有一处结论性错误），第三方许可声明缺失，UI 只有中文。
2. **工程化护栏**：`app` 层零测试、CI 只 lint 一个模块、无依赖机器人 / issue 模板 /
   发布自动化，改动越大回归风险越高。
3. **产品能力面**：与 ZENCHE、alpha-fairy、Sony Creators' App 相比，缺"后台自动导入、
   机内存储管理、USB/PTP 通道、取景辅助"这几块高频刚需。

## 1. P0：直接缺陷（建议本迭代内修完）

### 1.1 二维码配网：非 WPA / 无密码场景必失败

`feature/connection/QrScanViewModel.kt` 把密码无条件降级成空串：

```kotlin
val passphrase = info.password ?: ""
wifiManager.connectToCameraHotspot(info.ssid, passphrase, null) { ... }
```

而 `data/remote/wifi/CameraWifiManager.connectToCameraHotspot` 又无条件调用
`builder.setWpa2Passphrase(password)`。结果：

- 标准格式 `WIFI:T:nopass;S:...;;`（开放热点）→ 用空密码走 WPA2，必然 `onUnavailable`。
- `T:WEP` / `T:SAE` → 同样失败，且错误提示是"请检查 SSID 与密码"，误导用户。

`WifiQrInfo.authType` 已经解析出来了却没人用。建议：

1. 按 `authType` 分支：`nopass` 不设置密码（仅 `setSsid`），`WPA/WPA2` 走 `setWpa2Passphrase`；
2. `WEP`/`SAE` 明确提示"该认证方式不支持自动配网"，并给出跳转系统 WiFi 设置的手动入口；
3. 空密码 + 非 `nopass` 时直接判为二维码内容异常，不要发出去等 15s 超时。

### 1.2 相册落盘三缺：IS_PENDING / DATE_TAKEN / MIME

`data/remote/CameraRepository.kt` 的 `downloadToGallery()` / `commitToGallery()`：

```kotlin
val contentValues = ContentValues().apply {
    put(MediaStore.MediaColumns.DISPLAY_NAME, item.filename)
    put(MediaStore.MediaColumns.MIME_TYPE, mimeType)
    put(MediaStore.MediaColumns.RELATIVE_PATH, "${Environment.DIRECTORY_DCIM}/Imagedge")
}
```

- **缺 `IS_PENDING=1`**：下载中的半成品对图库/其他应用立即可见；大视频下载（数分钟）
  期间相册里就是一个打不开的残缺文件。正确做法是先 `IS_PENDING=1` 插入，写完再置 0。
- **缺 `DATE_TAKEN`**：`MediaItem.captureDate` 明明已经拿到了（枚举时 `GetObjectInfo`
  就有），却没有写进 MediaStore，导致下载回来的照片在系统相册里按"下载时间"排序，
  而非拍摄时间——这是相机传输类 App 最容易被用户一眼发现的问题。
  建议同时补 `DATE_ADDED`。
- **MIME 覆盖不全**：`inferMimeType()` 没有 `.heic/.hif/.tif/.tiff`，这些会落到
  `application/octet-stream`，却被塞进 `MediaStore.Images`。部分机型会用错误类型建索引，
  图库不显示。建议补全 HEIF/TIFF，并对未知类型改用 `MediaStore.Files` 或按扩展名兜底。
- 附带：ARW 用 `image/x-sony-arw` 建 Images 条目，部分 ROM 图库不识别；可考虑同时写
  `MediaStore.MediaColumns.IS_DOWNLOAD`? 更稳妥的是给 RAW 单独的落盘策略（可选：
  落到 `DCIM/Imagedge/RAW/`，并在设置里给"RAW 存相册 / 存目录"的开关）。

### 1.3 前台服务：Android 15+ 的 dataSync 时限未处理

`data/transfer/DownloadService.kt` 声明 `foregroundServiceType="dataSync"`。
Android 15（API 35）起，`dataSync` 前台服务有 **6 小时/天** 的运行上限，超时会由系统
回调 `Service.onTimeout()` 并强制停止。当前既没有实现 `onTimeout`，也没有在通知里
提示用户，长队列 / 大视频场景会被静默打断（且 `START_NOT_STICKY` 不会重建）。

建议：实现 `onTimeout(startId, fgsType)`（落库"已暂停，请回到前台继续"）并给出通知；
中长期把传输队列迁到 WorkManager（带 `setForeground`）或 `DownloadManager` 之外的自管
调度，把"6 小时预算"纳入设计。

顺带：通知没有 `setContentIntent`，用户点通知打不开 App；导出/传输完成也用同一个
通知 id 覆盖，没有"完成态"的收尾通知。

### 1.4 `PhotoViewerScreen` 的 `!!` 二次取值

```kotlin
viewModel.gridPreview(item) != null -> Image(bitmap = viewModel.gridPreview(item)!!, ...)
```

`gridPreview` 读的是 `MediaSessionCache.gridThumbnails`，而 `onTrimMemory` /
切浏览模式会把它清空——两次调用之间缓存可能已变，条件为真、取值却为 null，
直接 NPE 崩溃。改成先取一次到局部变量：

```kotlin
val fallback = viewModel.gridPreview(item)
...
fallback != null -> Image(bitmap = fallback, ...)
```

### 1.5 `rememberGlassLevel()` 不响应省电模式变化

```kotlin
@Composable fun rememberGlassLevel(): GlassLevel {
    val context = LocalContext.current
    return remember { glassLevel(context) }   // 无 key，永不重算
}
```

注释写着"省电模式变化时可感知"，但 `remember` 没有 key，进程存活期间不会重新求值：
用户开省电模式后玻璃依旧在每帧做离屏渲染。建议监听
`PowerManager.ACTION_POWER_SAVE_MODE_CHANGED`（或 `Configuration` 变化）后再计算，
把 `isPowerSaveMode` 作为 key。

### 1.6 其它小缺陷

| 位置 | 问题 | 建议 |
|---|---|---|
| `share/ExportManager.inSampleSize` | `size.maxLongEdge ?: if (size == ExportSize.M2) null else null` 恒为死分支，重构残留 | 删除该表达式，直接 `val target = size.maxLongEdge`，M2 分支单独处理 |
| `PtpChannel.startEventMonitor/startKeepAlive` | 用裸 `CoroutineScope(Dispatchers.IO)` 起协程，未绑定会话生命周期 | 用注入的 application scope（`SupervisorJob`）并在 `disconnect()` 统一取消 |
| `PtpChannel` 保活失败 | 只置 `DISCONNECTED`，不 `forceClose` 也不清 `client` 引用 | 保活判定断连时补齐资源回收，避免 fd 滞留到下次重连 |
| `DownloadService` 通知 | 无 `contentIntent`、无完成态 | 补 PendingIntent + 完成通知 |
| 可访问性 | ~~14 处 `contentDescription = null`~~ ——**复核为误报**：这些图标都位于带文字的按钮/行内，留空是避免重复播报的正确做法；真正需要标签的图标按钮（返回键等 12 处）都已用 `stringResource` 标注 | 剩余可做的是触控目标尺寸核查（多数为 36–40dp，低于 48dp 建议值）与 TalkBack 实机走查，优先级低于功能项 |
| `ExportManager` | PNG/WebP 无 EXIF 容器（已有 UI 提示，实现上也确实跳过） | 保持现状即可，但建议在导出结果里附一条"已去除元数据"的摘要，便于用户确认隐私策略生效 |

## 2. 一致性缺陷：文档、版本、许可

这类问题不影响运行，但直接决定第三方是否愿意信任和贡献这个项目。

### 2.1 README 与代码漂移（均已核实）

| README 声明 | 代码事实 |
|---|---|
| 徽章 `version-0.1.7` | `versionName = "0.2.0-alpha03"`（versionCode 1012） |
| `Android SDK (compileSdk 36)` | `compileSdk = 37`（全部模块） |
| 模块表只列 core/ptp/upnp/liveview/raw/lut/motionphoto/app | 实际还有 `:share`（0.2.0-alpha01 新增，导出+分享+EXIF 隐私）与 `:image`（编辑管线） |
| Features 无"分享"一节 | `:share` + `feature/share` 已实现尺寸档位/格式/EXIF 策略/系统 Sharesheet |

另外 GitHub 上 `main` 分支目前还没有 `share/`、`image/` 目录（发布线落后于开发线），
README 描述的功能与仓库内容进一步脱节。

**建议**：把 `versionName` 做成单一来源（`build.gradle.kts` 读 `gradle.properties` 或
版本目录），README 徽章改成 shields 动态徽章（`img.shields.io/github/v/release/mvpzac/Imagedge`
或 `badge/tag`），Requirements 与模块表随模块增删同步更新——最好在 CI 里加一条
"README 中列出的模块名必须与 `settings.gradle.kts` 一致"的校验脚本。

### 2.2 交接文档里有一处结论性错误

`docs/HANDOFF.md`（待办第 1 条）与 `.workbuddy/memory/2026-09-11.md`（薄弱点第 1 条）
都写着 `:image` 模块"**全项目零引用**"，建议"删除或落地"。实际上：

```
app/feature/edit/BasicEditViewModel.kt:10: import com.imagedge.camera.image.EditStep
app/feature/edit/BasicEditViewModel.kt:11: import com.imagedge.camera.image.ImagePipeline
app/feature/edit/BasicEditScreen.kt:38:    import com.imagedge.camera.image.EditStep
```

基础调整（亮度/对比度/饱和度/色温/旋转）已经跑在这条非破坏性管线上。这条错误结论会
直接误导贡献者删掉正在用的模块，属高优先级文档修复。

### 2.3 缺少第三方许可声明（合规风险）

仓库根目录没有 `THIRD_PARTY_NOTICES.md`，但代码里明确写了：

- `motionphoto/build.gradle.kts`：*"移植自 SuoxingTech/MotionPhotoLab（MIT License）"*
- `data/ble/SonyBleShutter.kt`：协议码表参考 `alpharemote`（**GPL-3.0**）与 `furble`（MIT）
- `ptp/`：结构参考 `libptp`（LGPL-2.1）、`Sony-ZV-E10-RX`
- LUT 资产：EditClips 生成 + 自研

MIT 要求"在复制或实质部分中保留版权声明与许可声明"，**移植代码必须补 NOTICE**。
GPL-3.0 的 `alpharemote` 是 Kotlin 项目、与本项目同类实现，是最需要小心的一个：
协议常量与行为事实不受版权保护，但**代码结构/表达受保护**。建议：

1. 新增 `THIRD_PARTY_NOTICES.md`，逐项列出组件、来源、许可证、是否含代码移植；
2. 在 `motionphoto` 源码头部保留上游版权行；
3. 给 `SonyBleShutter.kt` / `CameraControlViewModel.kt` 加一句"协议常量来自公开逆向与多实现互证，
   实现为本项目独立编写"的说明（你们已经在注释里写了依据，补一句明确声明即可）。

### 2.4 国际化完全缺失

UI 文案大量以中文字面量硬编码在 Kotlin 中（`PtpChannel.kt` 40 处、
`ExifFrameViewModel.kt` 35 处、`CameraControlViewModel.kt` 29 处…），
`res/values/strings.xml` 只有中文，没有 `values-en/`。README 是中英双语、
应用名与商店定位是英文，但 App 打开只有中文——这会直接挡住海外用户与
F-Droid 生态的收录。

**建议**：不要一次性全量抽取。先抽"主页/连接/相册/错误提示"四条主链路，
建立 `values-en`，其余按功能迭代补齐；玻璃 UI 的文案改动成本低，协议层的日志文案
（`AppLog`）可以保持中文不动。

### 2.5 机型兼容性矩阵

README 只声明"Tested with Sony ZV-E10 (firmware 2.03)"。对标项目里，
ZENCHE 有 50 款机型 profile + 实机验收清单，libgphoto2 有完整设备库。
建议新增 `docs/COMPATIBILITY.md`：机型 / 固件 / 连接模式（PC Remote、Send to Smartphone）
/ 通道（PTP-IP、UPnP、BLE、LiveView）/ 已验证功能勾选表 / 已知怪癖。
这份表也是社区 PR 最好的落点（"我测了 A7 IV，这里打勾"比提 issue 容易得多）。

## 3. 工程化与 CI

### 3.1 测试金字塔严重头重脚轻

- 现有 8 个单测全部在 `ptp / upnp / lut / raw / motionphoto`（算法与协议层），
  本次离线运行 `:ptp :upnp :lut :core` 全部通过。
- `app` 模块**连 `src/test` 与 `src/androidTest` 目录都不存在**；`:share`、`:image`
  同样没有测试。而 `app` 是 15,000 行、承担状态机与全部 UI 的模块。

建议按收益排序补：

1. `DownloadManager` / `AlbumViewModel` / `PtpChannel` 的状态机测试（Turbine + MockK，
   纯 JVM，成本低、覆盖的都是真机踩过的坑：取消、重入队、通道忙、断连快速失败）；
2. Compose 截图回归（Robolectric + Roborazzi 或 Paparazzi）——玻璃 UI 参数一改就是
   全局观感变化，人工看不过来；
3. 一条 instrumented 冒烟：启动 → 三 Tab 导航 → 无崩溃，把"零崩溃"从人工验证
   变成自动回归。

### 3.2 CI 覆盖面不足

`.github/workflows/ci.yml` 现状：`test` + `:app:lintDebug` + release/debug 构建。

- 只 lint 了 `:app`：`motionphoto` 有 57 条 baseline 却从未被检查，其他模块干脆没有。
  改成根任务 `./gradlew lint` 一次覆盖全部模块。
- 没有代码风格守门。你们实际风格相当统一（KDoc 模板、常量命名、`Config` 集中），
  加 ktlint/detekt 的边际收益很高、噪音很低。
- 没有 Dependabot、没有 issue/PR 模板。对这个领域而言，**bug 模板必须收集
  "手机型号 / 相机型号 / 固件版本 / 相机端模式 / logcat（CamRemote-*）"**，
  否则每条 issue 都要来回三轮。
- 发布是手工的（仓库只有 v0.1.8 / v0.1.9 两个 release，带 APK）。建议 tag 触发
  workflow：构建 → 附 APK → 附 SHA-256 → 从 CHANGELOG 截取对应段落作为发布说明
  （对标 ZENCHE 的"逐包 SHA-256 + 发布说明"做法）。

### 3.3 构建脚本与依赖目录的小问题

- 根 `build.gradle.kts`：`alias(libs.plugins.android.library) apply false apply false`
  重复了 `apply false`。
- `gradle/libs.versions.toml` 中 `ktor-*`、`xmlutil-*`、部分 `media3-*` 条目在
  全项目零引用（webapi 模块删除后的残留）。版本目录里保留未用条目会误导贡献者。
- `app/proguard-rules.pro` 在 `isMinifyEnabled = false` 下是死文件（开源决策可以保留
  不混淆，但要么删文件要么加注释说明"仅备用"）。
- `gradle.properties` 注释仍写"已验证兼容 AGP 8.11.2"，实际已是 AGP 9.4.0。
- Room `exportSchema = false` + 手写 `MIGRATION_1_2`，没有迁移测试；建议开 schema
  导出并在 CI 里跑 `Room` 迁移测试。
- 本机 `--offline ./gradlew test` 会因 `androidx.compose.ui:ui-tooling:1.12.0`
  未进本地缓存而失败（CI 联网环境无碍）。若要给社区提供可复现构建，可考虑加
  `gradle/verification-metadata.xml`（依赖校验）与 wrapper 校验和。

### 4.3 功能差距清单（按用户价值排序）

1. **后台自动导入**：Sony Creators' App 的核心卖点，ZENCHE 也做了。你们已有
   `captureEvents` + `contentEvents` + `silentRefresh` 的雏形，但只在遥控页工作态有效；
   应当做成"连接后可开启的常驻能力"（摄像机写卡 → 手机自动落盘 + 通知）。
2. **机内存储管理**：卷容量、文件保护状态、批量删除、拍摄后按需清理。你们目前只能读、
   不能删（ZENCHE 有完整的"从相机删除"流程与二次确认）。这是存储卡爆满时的真实痛点。
3. **USB/PTP 有线通道**：alpha-fairy、ZENCHE、digiCamControl 都支持。Android 侧走
   USB Host + PTP 可绕开相机 WiFi 的带宽与稳定性瓶颈，是"没带读卡器"场景的最强功能，
   也能让你的 App 在相机 WiFi 损坏/被占用时依旧可用。
4. **取景辅助 HUD**：直方图、峰值对焦、斑马纹、网格/安全框。成本低、感知强，
   是"专业感"的分水岭。
5. **传输侧增强**：分块续传按机型白名单恢复（协议实现已在，只差开关）、传输尺寸档位
   （分享模块的档位选择可复用）、增量"仅新照片"、完成通知可点击跳转。
6. **编辑管线统一 + GPU**：把 LUT / EXIF 边框 / 三格图 / 视频转 Live 收进 `:image`
   非破坏性管线；LUT 上 GPU；补曝光/高光阴影/白平衡/裁剪/曲线等"修图"能力
   （现在偏"特效"）。
7. **RAW 真解码**：目前只有内嵌 JPEG 预览。真解码后才能谈"修图"与"导出"。
8. **动态照片双向化**：Apple Live Photo ⇄ Android Motion Photo 互转 + 查看 + 拆分 +
   批量，这是独立的功能卖点（也是很好的引流入口）。
9. **发布渠道**：F-Droid / IzzyOnDroid / Obtainium 元数据。项目零 GMS 依赖、
   Apache-2.0、无追踪，天生适合 F-Droid；一次收录可持续带来自然流量。

## 6. 值得保留的做法

审查里挑刺容易，但下面这些是这个项目真正的护城河，改动时不要为了"重构美感"破坏它们：

1. **把真机教训写进代码契约**：`ptpMutex` 为什么必须是可取消的 suspend 锁、
   保活为什么不能 `forceClose`、切换功能模式为什么必须先等下载空闲——注释里都有
   原因和后果。这类知识比代码本身更值钱。
2. **纯协议模块零 Android 依赖**：`:core/:ptp/:upnp/:liveview` 可在 JVM 上直接单测，
   这是当前测试能覆盖协议层的前提。
3. **通道抽象与降级**：`CameraChannel` 的能力可选 + PTP 失败降级 UPnP + 断连判定
   排除 UPnP，边界划得很干净。
4. **失败路径的资源回收**：半成品文件删除、socket 回收、取消不写历史记录——
   这些"失败也要干净"的处理在同类项目里普遍缺失。
5. **双语 CHANGELOG 与决策留痕**：`CHANGELOG.md` 的"为什么改"写得很清楚，
   配合 `docs/sony-protocol-notes.md` 的协议笔记，已经是很好的社区资产；
   建议把协议笔记单独在 README 顶部做入口（它是这个项目最好的"技术名片"）。
